Did 80% definition recall hold up on unseen papers?

Almost. On 29 papers no setup had ever seen, the best self-hosted option, Qwen with three pooled passes, found 79.7% of the reference definitions: one match short of 80%. The original single-pass Qwen setup, which scored 83.5% on the development papers, found 69.0%. Opus with a plain prompt tied the pooled Qwen at 79.5%, at a cost of $41 for these 29 papers.

What "pooled Qwen" is

Pooled Qwen is the ordinary single-pass Qwen pipeline run three times over each paper, followed by one merge. Every pass is the same model, the same two prompts, the same verifier and the same filter. Only the format in which the model writes its answer changes: the original chat format, and a strict JSON format at two output lengths.

1 · Cut the paperinto overlapping text windows, twice: 16,000 characters (overlap 2,000) and 32,000 characters (overlap 4,000)
→
2 · Two promptsprompt A reads the 16k windows, prompt B the 32k windows; each lists terms with quoted definitions
→
3 · Combinemerge both lists per paper, dropping exact duplicates only
→
4 · VerifierQwen rereads each quote in its source window and drops non-definitions
→
5 · Relevance filtera small trained classifier drops definitions outside media-bias scope

Pooling repeats steps 1–5 in chat format (8,192 output tokens), JSON format (8,192) and JSON format (16,384), then merges the three final lists per paper. Why it works: even with fixed settings, the model's answers differ from run to run and more so across formats, so each pass finds some definitions the others miss. Why it costs: every unmatched prediction from each pass is kept too, so precision falls from 37% to 25%, about four predictions to review per correct one, and compute is about three times a single pass.

What the verifier and the filters do

The verifier

The verifier is a second Qwen call that checks, never writes. It gets the paper title, one exact source window and up to 16 candidate term/quote pairs. For each it answers whether the quote actually states what the term means (yes, no, uncertain). An example, a mention or a study result alone is not a definition. A candidate survives if at least one window says yes ("strict" policy). It can only delete definitions; it cannot edit quotes or add anything. In the Qwen setups it rereads the windows that produced each candidate; for Opus and Gemma it uses shared 32,000-character windows of the same paper.

The three relevance filters

All three are small logistic-regression classifiers on top of a fixed text encoder (BGE-base). They were trained on 1,171 human-labelled records from the 80 training papers, and their cutoffs keep 95% of relevant training records. None was fitted on DEV or TEST. They differ only in what they read:

  • Ordinary: the term and its definition (cutoff 0.309). Used in R6e24b3d and in the Opus and Gemma "+ filter" setups.
  • Title-aware: the paper title on a line above the term and definition (cutoff 0.237). Used in R0bea6bc and in every pooled pass.
  • Separate-title: title and term/definition encoded separately, side by side (cutoff 0.249). Used in Ra1da1ae.

How the prompt optimizers are doing

Three optimizers wrote the prompts. GEPA repeatedly rewrites the instruction using feedback on its mistakes, producing long prompts (5,000–15,000 characters, no examples). MIPRO proposes and tests shorter rewritten instructions plus one example. Bootstrap keeps the hand-written starting instruction (1,215 characters) and adds one worked example from a training paper. GEPA and MIPRO chose their prompts by scoring candidates on the DEV papers; Bootstrap never scored prompts on DEV.

  • Bootstrap held up better: Opus −7.5 (−10.5 with the filter), Gemma −6.4, SOOFI +4.2. MIPRO was mixed: Gemma −8.4, Sol +4.5 with a borrowed prompt.
  • At high recall the plain Bootstrap prompt did at least as well as GEPA: Opus 79.5% and Gemma 12B 71.0%, against 69.0% for single-pass GEPA Qwen. On TEST, GEPA is not the clean winner it looked like on DEV.
  • The GEPA prompts spell out concepts from the training papers they learned on, some of them quite specific ("fuzzy trace theory", "ratio bias"). None of the terms that occur only in DEV appear in any prompt. (A simple word check also turns up common words that happen to be TEST terms, such as "agenda", which the optimizer never saw; so these counts are rough.) The DEV inflation therefore came from picking the best of many noisy scores, not from DEV answers leaking into the prompts.
  • Caution: model and optimizer are tangled together here, and each row is a single run, so differences under about 5 matches (1.4 points) are noise.

What this means

  • The original 83% did not replicate. Single-pass Qwen lands at about 69% on unseen papers (about 75% on fresh DEV reruns).
  • Pooled Qwen is the pick by the frozen rule: 79.7% recall, 24.8% precision, self-hosted at $0. Treat it as "about 80%", not a guarantee: it is one run, and TEST also picked the winner among 12 rows, so it is slightly optimistic.
  • Opus is not affordable at scale (about $4,200 per 4,000 papers against about $47 left on the OpenRouter key), so it stays a comparison point.
  • Two setups failed operationally and could not be picked: Opus with the borrowed Qwen prompt (billing safeguard stop) and Sol (one paper with no output). Neither was near 80%.
  • Next: run pooled Qwen over the full paper set on ZIB, then collect the papers those definitions cite (one level of citations only), convert them to text and extract from them the same way.

Terms used

Reference definition
A definition annotated by people in a paper; TEST has 365 across 29 papers.
Match
A predicted definition paired with one reference definition of the same paper by the frozen similarity matcher (score 0.50 or more). Each prediction can match at most one reference.
Recall / precision / F1
Share of reference definitions found / share of predictions that match / their harmonic mean. Unmatched predictions are not necessarily wrong, only unannotated.
DEV, TRAIN, TEST
21 development papers used to choose setups, 80 training papers used to write prompts and train filters, 29 held-out papers used only here.
Window
A slice of a paper's text given to the model in one request; measured in characters, not tokens.
Pass
One complete run of the pipeline over all papers.
Combine / pool
Merge several lists of records, removing exact duplicates only (earlier reports called this the "union").
